Trigger

From one switch to many

I was quite burnt out this week. I was trying to understand what machine code and a programming language actually are, what the differences are, and what builds a programming language. I also looked at symbol systems: how a symbol is created in the first place.

References

What builds a programming language?

I started by mapping how a computer runs a program, from my own slides (below) to the chain of tools behind a language: Flex, Bison and LLVM. The full picture is in the next section.

I also took notes on Florian Cramer's Words Made Flesh, on computation as a figure of thought. Two pairs mattered most. Syntax vs semantics: syntax is an abstraction from human language; semantics are the metaphors and handles that give it meaning. Artificial vs natural language: an artificial language works through a purely formal, syntactical metalanguage, separate from natural language, like the binary code 00001.

Understanding

How a computer runs a program

To build a programming language, I have to understand what each part of one does. Here is the path from the switches inside a machine to the code a person writes, mostly following Robert Nystrom's Crafting Interpreters, a guide to building languages, and Abelson and Sussman's Structure and Interpretation of Computer Programs (SICP).

1. Switches and machine code

At the bottom, a computer is switches: on or off, 1 or 0, like my open and closed hand, or a hole in a punch card. Machine code is the only language a CPU understands directly: sequences of instructions encoded as bits, specific to that chip. Code written for one kind of processor (x86) will not run on another (ARM). Bits are grouped into bytes of eight, and because long rows of 0s and 1s are hard to read, people usually write machine code in hexadecimal (base 16): the byte 10110000 is written B0.

2. Assembly

Assembly language gives each machine instruction a readable name, usually one line per instruction. It is still tied to one chip, but people can read it. It was the first step from switches towards words.

3. High-level languages and source code

Languages like JavaScript, Python or Processing let people write in something closer to human language. What a person writes is source code, which to the machine is “literally just a string of characters” (Nystrom). Everything after this is about turning that string into something a CPU can run. Nystrom pictures it as climbing a mountain: up through analysis until the program's meaning is clear, then down towards the machine.

4. Scanning: characters into tokens

A scanner (or lexer, like Flex) reads the characters and groups them into “words” called tokens: a number like 123, a name like min, a bracket. It throws away what means nothing, such as spaces and comments.

5. Parsing: tokens into grammar

A parser (like Bison) takes the flat list of tokens and builds a tree that mirrors the grammar: which parts nest inside which. This is the syntax tree. The parser also reports syntax errors when tokens are combined in ways the grammar doesn't allow. Nystrom notes that many parsing techniques “were originally conceived to parse human languages by AI researchers”, but human languages turned out to be too messy for rigid grammars, while the simpler grammars of programming languages fit them perfectly.

6. Analysis: what the names mean

With the structure known, static analysis works out meaning: what each name refers to (binding and scope) and, in some languages, whether types fit together. The scanning, parsing and analysis together are called the front end. This is the summit: the program's meaning, its semantics, is now visible.

7. Intermediate representation and optimisation

The code is often turned into an intermediate representation (IR), a form tied to neither the source language nor the machine, which lets one language target many machines. Once the meaning is clear, the compiler can optimise: swap in a faster program with the same meaning, for example by doing fixed arithmetic in advance.

8. Code generation, virtual machines and runtime

Code generation turns the program into instructions to run: real machine code, or bytecode for an imaginary, idealised machine. A virtual machine is a program that pretends to be that machine, which makes the language portable. Finally the runtime: the services a language needs while the program runs, such as managing memory.

9. Compiler, interpreter, transpiler

  • A compiler translates source code into another, usually lower-level form, but doesn't run it. The user runs the result.

  • An interpreter takes source code and runs it straight away, “from source”. A tree-walk interpreter runs the syntax tree one node at a time, which is common for little languages.

  • A transpiler compiles into another high-level language and lets that language's tools do the rest. “Web browsers are the ‘machines’ of today, and their ‘machine code’ is JavaScript.” p5.js and Hydra both run on JavaScript in the browser.

  • The line between compiler and interpreter is blurry. Nystrom compares it to fruit and vegetable: Python, for example, is an interpreter that also compiles to bytecode inside.

10. What every language needs

SICP gives a test for any language: “Every powerful language has three mechanisms”: primitive expressions, the simplest things the language deals with; means of combination, for building compound things from simpler ones; and means of abstraction, for naming compound things so they can be used as units. It also says “programs must be written for people to read, and only incidentally for machines to execute.”

What I understood

I finally understood what a compiler is. Seeing the whole path also showed me where my own work sits: I am working at the level of the compiler, interpreter and transpiler, turning gestures into something that runs. The rest, down to machine code, I can't really design.

This also set a boundary for the project. I don't think I am expert enough to design a programming language from scratch. As a designer, I can understand how it works and see where I can step in: where I can create a sense of agency, or a system I can work off. Using what we already have and adding my own spin on it is enough.

Experiment

Repetition and values

Idea. Form + Code: repetition as the core of syntax.

Why. In code I often need numbers that change, not just on or off. In human language I would say “a smaller circle”; in machine language that is decreasing a number. I wanted a hand to hold a value, and to see whether rules like repetition, a for loop, could be visualised.

How. Version 1: a grid of repeating images, where open or closed decided fill or no fill. Version 2: the hand-tracking confidence value decided the shade of grey, with a shorter response time for more variation. Version 3: two hands.

Reflection. With one variant it got boring, and two shades didn't create the movement repetition is supposed to have. Keegan tried version 2: they reached for two hands instinctively, found it too fast without an instruction, and wanted an indication of where the value was gathering. Version 3 made interesting repetition, but it was hard to focus on two things at once when both hands were needed to fill one square. In my notes I asked: what is AI's role in this? And was it interesting, or only interesting-ish?

Why a grid. A grid is the basis for starting a generative visual, so I started there. The idea was a for loop filling in the squares. But instead of having random blacks, how about using my hand to input those values?

Zhiqi also tried the grid: holding a closed hand fills the current cell, one cell at a time across the grid.

Reflection

Reflecting

Back-talk. Two kinds this week. The machine misread my fingers in the alphabet, and Keegan instinctively reached for two hands, asked for an instruction, and wanted to see where the value was.

What I learned. With only two shades, repetition did not create movement. The hand had to hold a value, not just on or off.

How I was framing it. My idea of a designer-friendly language hasn't really changed. But there is maybe a shift towards asking what your body can create, or what your body can write. At this point I was still trying to figure out the lines.

Moving Forward

Binary was too technical, and the grid showed me that a hand can hold a value. The next step was to stop controlling visuals and start defining what each gesture means.
